# v0.12.0 plan: perf + 100% coverage

This document records findings from the v0.11.0 work and the plan for v0.12.0.
No code was written as part of this plan; it is a design/audit artifact only.

## 1. Where coverage stands after v0.11.0

Total statement coverage is ~92.2% across the packages. The remaining gaps fall
into three categories that cannot be closed by adding more black-box tests:

| Package | Uncovered symbol | Why it is uncovered |
|---------|------------------|---------------------|
| `main` | `main()` | Calls `os.Exit(1)` on error, which kills the test process. The `run()` function is covered. |
| `tui` | `handleNormalKey`, `Update` branches, `handleSearchKey` variants, `runTLDR`, `yankAll`, `openInEditor`, `refreshViewport`, `View`, `RunDiffViewer`, diffmodel render functions | Bubble Tea key-handling paths that require a terminal / `tea.KeyMsg` with specific key strings not exercised by existing tests. Some are behind `showHelp` toggles or `pending*` state flags. |
| `config` | `ResolveIn` error path when `globalConfigPath` fails (`XDG_CONFIG_HOME` set to a non-existent dir AND stat fails) | `globalConfigPath` only errors when `XDG_CONFIG_HOME` is unset AND `os.UserHomeDir` fails, which is hard to trigger deterministically in a test. |
| `core` | `extractCSS` non-404 non-OK HTTP status, `ReleaseExists` default-status error, `ensureVersion` non-fresh non-force path, `readCustomProp` early-return branches, `CompareSelectors` uncovered-list truncation edge, `TLDRResult.String`/`StatString` parts lists | Network/status/error branches and UI-render branch coverage. |

### Refactor strategy to reach 100%

Rather than adding fragile tests for terminal/keyboard interaction, refactor so the untestable thin shells delegate to testable pure functions:

1. **`main()`** — Extract `run()` is already extracted and covered. `main()` itself is a 4-line shell that calls `os.Exit`. Accept it as an unavoidable runtime boundary (documented exception), or move `os.Exit` out of `run()` so `run()` returns an error and `main()` only converts it. The latter keeps `main()` at 0 statements but makes `run()` fully covered (already is).

2. **TUI handlers** — The `handle*Key` methods are large switch statements on `msg.String()`. Extract each key branch into a pure function taking `(model, key string) (model, cmd)` so it can be unit-tested without `tea.KeyMsg` construction. Candidates:
   - `handleTableKey` (largest, ~50 lines, 83.3%)
   - `handleSearchKey` (~96.8%)
   - `handleConfirmKey` (~83.3%)
   - `handleNormalKey` in diffmodel (~82.2%)
   - `render*` family in diffmodel (84.6%–96.6%)

   After extraction, tests can call the pure functions directly with synthetic key strings, covering every branch.

3. **`config.ResolveIn` global-config-error path** — Make `globalConfigPath` injectable or split the "resolve path" logic from the "stat the file" logic so the error branch (stat returns non-NotExist error) can be triggered.

4. **`core` error branches** — Add targeted unit tests using `httptest` servers returning non-200/non-404 statuses for `ReleaseExists` and `extractCSS`, and an aged-but-not-fresh entry for `ensureVersion`. These are already partially covered; the remaining slivers are small.

### Acceptable residual exceptions

If 100% proves impractical for `main()` and a few TUI key branches, document them as intentional runtime boundaries in a `coverage.except` note and keep the rest at 100%. The Makefile `cover` target prints per-function coverage; CI can assert everything except the documented exceptions is 100%.

## 2. Performance audit — all commands / flags / internals

### `ocd check` (`cmd/check.go`)

**Fixed in v0.11.0:** `app.css` was parsed twice — once via `core.ExtractCSSVariables(string(css))` and again via `core.ParseCSS(string(css))` inside `CompareSelectors`. Now parsed once into `targetIdx` and reused.

**Remaining:** None significant. The theme is read once via `core.ReadTheme`, which caches its `Index`. `CompareVariables` is O(target + theme). `CompareSelectors` is O(target × theme) in the worst case (see selectors below).

### `ocd stat` / `ocd diff --tldr` (`cmd/stat.go`, `cmd/diff.go`)

Both call `core.AnalyzeCSS(string(css))` / `core.AnalyzeDiff(diff)`. These split the entire CSS into lines and run **eight compiled regexes per line** (`cssVarRe`, `selectorRe`, `importantRe`, `hexRe`, `rgbRe`, `hslRe`, `oklchRe`, `otherColorRe`, plus `varSelectorRe`). For a 420 KB minified app.css (~15k lines), that is ~120k regex applications per analyze call. The diff path runs this on the unified diff output, which can be larger than the source CSS.

**Bottleneck:** regex-per-line on large CSS. Not catastrophic for single-version stat/diff, but compounds if called repeatedly.

### `ocd origin` / `check --compat-sweep` (`cmd/origin.go`, `cmd/check.go`)

Both call `core.EnsureAllCSS` then `core.FindOrigin` / `core.FindOrigins`.

- `EnsureAllCSS` (sweep.go): Phase one probes every version needing a download with a HEAD request in parallel (DefaultSweepConcurrency=8). Phase two downloads available versions, several at a time. Correct design; the HEAD-probe-first optimization avoids downloading the ~10 versions with no release.
- `FindOrigins` (compat.go): Parses each version's app.css **once** in parallel via `ParallelFor`, building a presence matrix `[version][target]`. This is the right asymptotic shape (O(versions × targets) parse work, not O(versions × targets²)). `scanTargets` reads the file and parses with `ParseCSS`.

**Bottleneck:** For a full sweep across ~108 versions, each parse is ~6 ms (flexcyon theme figure; app.css is larger), so a cold sweep is seconds of CPU plus network. Acceptable for a one-time sweep; repeated sweeps re-parse cached files because `scanTargets` reads from disk each call. No in-memory cache of parsed indexes across `FindOrigins` calls — if `origin` is run multiple times in the same process (it isn't; CLI is one-shot) this would matter. Not a CLI-level concern.

### `ocd extract` / `ImportFile` (`cmd/extract.go`, `core/extract.go`, `core/asar.go`)

- `extractCSS` downloads the full `.asar.gz` (~9 MB), decompresses to a temp file, then `extractAppCSSFromASAR` reads the ASAR header and copies `entry.Size` bytes via `io.NewSectionReader` + `io.Copy`. Correct and atomic (`extractCSSAtomic` → rename).
- `ImportFile` for `.css` uses `copyFileAtomic` (temp + rename). For `.asar` uses `extractCSSAtomic`.

**Bottleneck:** None for single extractions. The ASAR parser reads the whole JSON header into memory (bounded by `asarMaxHeaderSize = 10 MB`) — fine.

### `ocd clean` (`cmd/clean.go`)

`os.RemoveAll(core.CSSDir)` wipes the whole cache. Labelled clean removes one dir. Trivial, no bottleneck.

### `ocd interact` (`cmd/interact.go`, `internal/tui/model.go`)

- `fetchData` calls `m.fetcher.FetchAll(m.force)` — parallel fetch of RSS, Docker Hub, Electron (3 goroutines via `errgroup`). Each source has its own `http.Client` with a 15 s timeout.
- `buildRows` iterates all RSS versions, sorts them, and for each does an `os.Stat` on the cache path to compute CSS status. For ~108 versions that's 108 stat calls — negligible.
- `applyFilters` iterates all rows per keystroke; for each row with `!m.showEarlyAccess` it does a linear scan of `m.result.RSS` to find `IsEarly`. With ~108 rows and ~108 RSS entries, that's up to ~11k comparisons per filter change — negligible but O(n²)-ish. Trivial at this scale.
- `loadTicker` sleeps 2 s artificially — a UX delay, not a perf bug.

**Bottleneck:** `FetchAll` is the network-bound step; no CPU bottleneck. `applyFilters` linear-scan is fine at current scale but would benefit from an `IsEarly` lookup map if RSS grows.

### `ocd diff` TUI viewer (`cmd/diff.go`, `internal/tui/diffmodel.go`)

- `core.DiffCSS` reads both app.css files and runs `myers.ComputeEdits` on the full strings, then `gotextdiff.ToUnified`. For two 420 KB files this is the diff algorithm on ~840 KB total — Myers is O(N·D) where D is edit distance; for similar versions D is small, so fast. The `hasDiff` scan splits the entire unified diff into lines and checks prefixes — O(diff size).
- `diffModel` parses the unified diff into `[]parsedLine` once at init (not shown fully, but `parsed`/`hunkIdx` suggest a single pass). Render functions build strings per frame via `strings.Builder` and `lipgloss`. Side-by-side mode splits lines and measures widths.

**Bottleneck:** The unified diff string can be large (tens of KB to MBs for major version jumps). `DiffCSS` builds one big `diff` string and `AnalyzeDiff` (if --tldr) re-splits it into lines and runs regexes per line. Acceptable for interactive use; no caching of parsed diff across redraws (each `View` call re-renders from `parsed`, which is fine since `parsed` is precomputed).

### `internal/core/cssparse.go` — `ParseCSS`

Byte-by-byte scanner over the whole source. Allocations:
- `sel []byte` buffer reused via `flushSelector` (reslices to len 0, keeps capacity) — good.
- `splitSelectorList` allocates a `[]string` per rule and substrings — one allocation per selector list.
- `readCustomProp` returns `name`, `value` as new strings (substring of `src`, no copy in Go 1.x since strings share backing memory — actually `src[start:j]` shares the backing array, so no copy).
- `skipString` walks bytes; `strings.Index` for comments.

**Bottleneck:** Per-byte switch in Go is reasonably fast; the 6 ms figure for 742 KB confirms it is not a hotspot. No change needed.

### `internal/core/selectors.go` — `CompareSelectors` / `SelectorCovers`

This is the most significant algorithmic bottleneck:

```go
for sel := range targetIdx.Selectors {          // outer: target selectors (~3300 for v1.6.3)
    if themeIdx.Selectors[sel] { ... }          // O(1) exact match
    covered := false
    for _, ts := range themeSels {              // inner: theme selectors (small for themes)
        if SelectorCovers(ts, sel) { ... }      // splits both selectors, walks parts
    }
}
```

- `SelectorCovers` calls `splitSelector` on both theme and target selectors, then walks parts calling `compoundCovers` which builds `map[string]bool` for classes/ids via `compoundTokens` (allocates two maps per call).
- For a theme with few selectors (flexcyon: 3 selectors) vs target with 3303, the inner loop is 3 × 3303 = ~10k `SelectorCovers` calls, each allocating maps. Trivial.
- For a large theme (hundreds of selectors) vs a large target (thousands), this becomes O(T × S) with map allocations per pair — could be millions of allocations. **This is the worst-case perf cliff in `check`.**

**Recommendation:** Precompute a per-compound signature (set of classes + ids) for theme selectors once, then match target compounds against signatures instead of re-splitting and re-tokenizing per pair. Also cache `splitSelector` results per selector string (they are immutable).

### `internal/core/sweep.go` — `ParallelFor`

```go
tokens := make(chan struct{}, limit)
group.Add(n)
for i := 0; i < n; i++ {
    go func(i int) { ... fn(i) ... }()
}
```

Spawns one goroutine per version (up to ~108) with a semaphore channel. Fine for n ≤ ~108. `limit > n` clamps to n, so at most n goroutines. No leak (all `group.Done`). Acceptable; could use a worker pool but not necessary at this scale.

### `internal/sources/fetcher.go` — `FetchAll`

Three `errgroup` goroutines, each checking cache then fetching. `http.Client` timeout 15 s each. No shared connection pool issues (each source has its own client). Correct.

### `internal/cache/cache.go` — `Store`

JSON file per entry. `Get`/`Set`/`Delete`/`Clear` all do filesystem ops. `Clear` reads dir names then removes each. No in-memory cache; every `Get` is a disk read + JSON unmarshal. Used only for metadata (RSS/docker/electron), tiny payloads. No bottleneck.

## 3. Recommended v0.12.0 work items (no code yet)

### A. Coverage → 100% (refactor-led)

1. **TUI key-handler extraction** — `internal/tui/model.go` and `internal/tui/diffmodel.go`: extract pure `handle*(key string)` functions from the `tea.KeyMsg` switches. Add unit tests covering every branch (help toggle, search backspace/enter/tab/char, confirm y/n/q, next/prev hunk, scroll, yank line/hunk/all, open in editor, render branches).
2. **Config path injection** — Make `globalConfigPath` testable so the stat-error branch in `ResolveIn` is coverable.
3. **Core error-branch tests** — `httptest` servers returning 503/403/etc. for `ReleaseExists` and `extractCSS` non-200/non-404 paths; aged-not-fresh entry for `ensureVersion`.
4. **Document exception** — `main()` `os.Exit` boundary; note it as intentional.

### B. Performance

1. **Selector comparison optimization** (`selectors.go`) — Precompute per-compound class/id signatures for theme selectors; cache `splitSelector` results. Reduce `CompareSelectors` from O(T×S×alloc) to near O(T + S×signature-matches). This is the largest single algorithmic win for `check` on large themes.
2. **TLDR regex consolidation** (`tldr.go`) — Combine the 8 per-line regexes into a single pass where possible (e.g. one regex for color formats, or scan bytes instead of `regexp` per line). Only worthwhile if profiling shows `stat`/`diff --tldr` on large CSS is slow.
3. **`applyFilters` IsEarly lookup** (`tui/model.go`) — Build a `map[string]bool` of early-access versions once in `buildRows`; consult it in `applyFilters` instead of linear-scanning `m.result.RSS` per row.

### C. Validation

- Run `make cover` and assert every function except documented exceptions is 100%.
- Benchmark `ocd check` against flexcyon before/after the selector refactor.
- Benchmark `ocd stat` and `ocd diff --tldr` on a large app.css before/after any tldr.go changes.
